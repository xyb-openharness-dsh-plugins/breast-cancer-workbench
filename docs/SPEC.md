## 4. 产品立场（D16：诊断归医生，信息是边际价值）

### 4.1 一句话

**工具不判断病情；工具把散落的信息整理成可核对、可回溯、可带去讨论的样子。**

"边际"指：这些信息原本也在，只是散在出院小结、化验单、微信记录和记忆里；工作台把它们放在一处，并标清楚**来源、日期、测量方法**。

### 4.2 三类输出，严格分开

| 类型 | 例子 | 允许的输出 | 禁止的输出 |
| --- | --- | --- | --- |
| 事实 | 10-14 患健侧臂围差 1.8cm，四点位最大，坐位 | 原样展示 + 来源 + 方法 + 日期 | 补一个"正常范围"下结论 |
| 派生 | 较上次 +0.7cm；四次趋势；BMI | 展示计算过程与口径 | 命名为"恶化"「好转」并着色 |
| **看法** | "我觉得手臂比以前沉"、"担心是不是复发了" | 存为**一条带主体的信息**，标注"这是我的看法/担心，不是医生结论"，可修改、可撤回、默认不进事实区 | 升级为结论、写进摘要的"病情"栏、参与图表、被 Agent 当成事实 |

### 4.3 界面与文案硬约束

1. 任何涉及"是不是/要不要"的句子，主语只能是**治疗团队**：例如"是否需要处理由治疗团队判断"，不能写"建议就医"之外的判定。
2. 2cm 参考线、参考区间等一律标注"提示进一步评估的常用口径，具体待专业确认"，不写成诊断阈值。
3. 看法与症状分开存：症状是 0–3 强度（体验），看法是文本（观点）。二者都不进检验曲线。
4. 导出按"事实 / 派生 / 我的看法与担心 / 想问题目"分区；看法区标题固定为「以下是我的看法与担心，不是医生结论」。
5. AI（二期开关）只能引用事实区与派生区，引用看法时必须带"这是用户自述"。

### 4.4 AI 范围（沿用 D05）

一期：整理、回溯、生成提问草稿。二期开关：结合个人资料、带来源的解释与可讨论选项，默认关闭，开启时逐次说明发送内容。

### 4.5 治疗相关器官毒性与敏感话题（v0.8，HVT 补丁）

**LVEF 与骨密度只做"与治疗同窗的记录"，不做毒性判定。** 正在或曾经使用蒽环类、抗 HER2 的患者，可记录 LVEF 数值、检查日期、测量方法（echo/MUGA/其他原文）与机构；正在使用 AI 的患者，可记录腰椎 DXA 的 T 值、检查日期与机构。两项都与治疗事件同轴显示，页面常显"这是检查结果记录，是否继续或调整治疗由治疗团队决定"。

不做什么：不设"下降多少算毒性"的阈值提示，不生成心脏毒性或骨质疏松的判断，不给钙/维生素 D 剂量，不因单次变化建议复查频率。LVEF 的"基线"取用药前还是术前，属待专业核验项（见 HVT-REVIEW U2）。

**内分泌副作用与放疗皮肤：记录体验，不做归因。** 关节痛/僵硬/潮热按 0–3 自评强度记录，**用强度轨道呈现，不画成趋势曲线**；可记部位与时间，并与用药时间对照；不出现"这是药引起的"这类归因句，不评价是否继续用药。放疗皮肤反应记录部位（对应放疗野）、外观描述原文、是否已联系团队；分级只引用院方原文，不自拟。

**生育与性健康是可选话题，不是必填表。** 提供"可以问的问题"清单（化疗/内分泌对生育的影响、是否需要转介、月经变化要不要说、避孕与性生活的沟通），可只记一句"我想问这个"；生育意愿、月经状态、是否已转介均为自愿填写。不给"能否怀孕"的结论、不按年龄推断、不推荐具体生殖中心；默认私密，沿用 `DATA-FLOW-SPEC` 的三处过滤。

**术式与身体形象。** 术式（保乳/全乳切除/改良根治/重建，含即刻或延期）是独立字段，不与其他治疗混写；身体形象话题由用户主动打开，默认不出现在摘要与导出。

| 材料 | `document`、`parse_job`、`candidate` | 原件与哈希、解析任务与失败态、待核对候选字段 |

| 临床 | `diagnosis_note`、`biomarker`、`treatment_event` | 病理转录（不判定）、标志物、治疗事件（计划/实际分开） |
| 指标 | `metric_definition`、`observation`、`measure_protocol`、`measurement`、`arm_set` | 指标字典版本化；检验值；测量协议；单点测量；四点位一次测量成组 |
| 体验 | `symptom_entry`、`viewpoint`、`care_entry` | 强度症状（不进曲线）、**看法/担心（信息，非结论）**、康复与日常记录 |
| 行动 | `task`、`question`、`saved_result` | 待办、问题（有版本）、已保留结果（快照） |
| 外部 | `trial_snapshot` | 试验快照（一期只做样例与界面演示） |
| 产出 | `export_job`、`change_log` | 导出快照与过时标记、变更审计 |

三条跨表铁律：

1. **事实、派生、看法、结论四类不混表、不混栏。** 派生值只算不存（除导出快照与写入时固化的配对差值），看法只进 `viewpoint`。
2. **可比性跟方法走。** `observation` 看 `lab_method`，`measurement` 看 `protocol_id` + `assessor_role`；不同方法不连成一条线。
3. **更正不覆盖。** 新值 `supersedes_id` 指向旧值，旧值保留并标 `superseded`；导出与摘要据此判断是否过时。

共 **25 张表**。DDL 已在内存 SQLite 实跑通过（建表、索引、`viewpoint.is_conclusion=0` 与枚举 `CHECK` 均生效），但**字段是否够用、口径是否认同仍待 G3 评审**。

## 6. 数据流摘要（D19）

完整定义见 [DATA-FLOW-SPEC](DATA-FLOW-SPEC.md)。

```
① 导入原件 → ② 解析任务（可失败，原件保留）→ ③ 候选字段（带出处）
→ ④ 用户逐项核对（接受/改/拒）→ ⑤ 写入 record + observation/measurement
→ ⑥ 读取时实时派生（差值、趋势、BMI、提醒）→ ⑦ 各页读模型（看板/一图秀/卡片）
→ ⑧ 问题与摘要（快照，可标过时）→ ⑨ 导出与发送（范围受控）
```

三类数据的更新语义（这是数据流的核心，不是"全部实时刷新"）：

| 类型 | 例子 | 语义 |
| --- | --- | --- |
| 事实型 | 化验值、引流量、臂围、体重 | 写入即生效，读取时实时计算，不缓存副本 |
| 派生型 | 差值、趋势、BMI、提醒文案 | 不落库，读取时算；口径写进合同，避免两页算法不一致 |
| 结论型 | 摘要、导出、问题清单、AI 生成内容 | **不静默重算**：来源变更后标"已过时，建议重新生成"，保留旧快照可回溯 |

## 8. 技术路径

| 路径 | 判断 |
| --- | --- |
| 社区原生插件 + 模块化服务 + SQLite + 文件目录 | 建议采用；复用宿主合同，适合版本与跨页关联 |
| 原生插件 + JSON 文件 | 仅配置或早期样例，不作事实库 |
| 独立 Web 应用 | 需自建登录与同步，偏离本机工作台目标，暂不建议 |

API-first：领域/数据合同 → 业务服务与 API → UI 与编排 → 原生会话适配。包结构沿用 `package.json`、`cordis.patch.yml`、`dsh/index.js`、`lib/client.js`。存储实现等 G3 通过后按 [SCHEMA-SPEC §9](SCHEMA-SPEC.md) 的迁移计划落地。

布局：**A 标准分栏**（D21 → D34，2026-10-17 定）——`businessSide: 'right'`、`businessWidth: 0.65`、`customFrame: false`。业务区在左、右侧宿主原生会话；936px 等效宽度下 34 个视图无页面级横向溢出，「测量记录」六列表改为整行跨列，不再靠横向滚动藏列。实测与规则见 [UI-DESIGN §5.6](UI-DESIGN.md)，参数唯一来源为 `lib/layout.js`。原型为独立页面，不模拟宿主聊天。

版本号：单一来源为仓库根目录 `VERSION`，页面三处（顶栏 / 页脚 / 关于）由同一常量渲染，构建时注入、不手写第二份；规则见 [VERSIONING](VERSIONING.md)，校验 `node scripts/check-version.mjs`。

## 9. 开发顺序（受闸口约束）

1. **G1**：确认模块、场景、边界（已完成）。
2. **G2**：v0.3.0 已通过（简化）；15 页逐页表可在开发期补签。
3. **G3**：评审 SCHEMA-SPEC / DATA-FLOW-SPEC；改完再冻结。**这是 M1 的入口。**
4. **M0**：工程底座（`package.json`、脚本、版本注入、占位测试）——不等 G3。
5. G3 通过后：建表与迁移 → 主线闭环（资料→草稿→档案→一图秀→上肢→导出）→ 外围模块 → 设置 → 接入 DSH → 发布。里程碑与判定见 [DEV-PLAN](DEV-PLAN.md)。
6. 独立审查与真实用户走查各一次，结果如实记录。

未过闸口不开发后端；模拟保存、脚本检查、静态截图都不算确认。

## 10. 接入与发布（G3 之后，单独一本手册）

完整步骤、命令、判据与记录表见 [RELEASE](RELEASE.md)。此处只钉四条：

1. **接入顺序**：G2 已通过 → G3 评审通过 → 临时目录生成骨架 → 按文件合并（`docs/`、`prototypes/`、`assets/` 以本仓库为准）。
2. **版本验证分三层**：V1 包级（pack 清单、体积 ≤8 MiB、敏感文件、SHA-256、`VERSION` 与清单一致）→ V2 装机（配置 / 已安装列表 / 真实界面三种证据，**界面必须能看到 vX.Y.Z**）→ V3 业务（官方《工作台开发规范》§8 + 本文 A1–A33）。**缺一层不能叫通过。**
3. **发布分两步，互不等同**：P1 推 Git（只推授权范围）、P2 市场投稿（单独确认）。"PR 已合并"不是"上架"，会话、项目文件在卸载后必须保留。
4. **医疗类额外红线**：简介不写疗效/诊断承诺；截图必须来自最终可安装版本且完全脱敏；包内不得含真实病历、数据库、本机路径。

当前阻塞（2026-10-17）：仓库 `owner/repo`、包名 scope、首发版本号三项未定；许可证已定 **MIT**，布局已定 **A 0.65 标准分栏**（D34）。见 RELEASE §8。
